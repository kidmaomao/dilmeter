# 连续出线演示与视频对照

参考：[【自制】少人局牢马50%](https://www.bilibili.com/video/BV1bH9sBXEW9/)。视频总长约 4 分钟，前段是游戏录像，后段是模拟器操作；二者不能混为同一套测量数据。

## 可重复核对的出线节奏

在后半段约 03:36.93 起，按红色条带首次出现采样一组可连续跟踪的射线，原始视频为 30 fps。时间值按帧估计，保守误差约 ±0.07 秒；重叠颜色、附加射线及遮挡使这组记录不能代表所有来源的全部射线。

| 相邻可跟踪射线 | 视频时间（秒） | 间隔约值 |
| --- | --- | --- |
| 1 → 2 | 216.933 → 218.200 | 1.27 s |
| 2 → 3 | 218.200 → 219.300 | 1.10 s |
| 3 → 4 | 219.300 → 220.233 | 0.93 s |
| 4 → 5 | 220.233 → 221.033 | 0.80 s |
| 5 → 6 | 221.033 → 221.800 | 0.77 s |
| 后续多次 | 如 222.567 → 223.333 | 约 0.76–0.77 s |

这一段呈现先加密、随后维持高频的节奏，并不能证明实战必定按相同数列加速，也不能根据一组出线反推出唯一机制公式。数据见 `demos/brontas-guide/cadence-reference.json`。

## 与上一版 GIF 的区别

旧版 16 秒 GIF 是横线、纵线、交叉线和数据中断的独立功能样例；只有三组预设时序，没有连续出线周期。新版 20 秒 GIF 有 2 秒入场示意、完整 15 秒倒计时、归零后继续观察以及结束段。新射线加入时保留尚未结束的旧射线，规划器同时检查全部输入。

射线出现间隔采用上表；射线方向/通道序列参考该段网格分布并做示意，位置严格映射至边界相接的三列/三行，人物由测试脚本移动，不逐帧复刻视频操作。入场人数和计时起点由演示脚本设定，并未新增真实阶段计时识别。

## 不能从画面直接确认的参数

- **预警到致命的延迟不是出线间隔。** 游戏特效变色不等于已经造成伤害，视频文字也提醒动画持续时间与即死判定不同。本次没有测得可靠的逐条伤害时刻。
- 新版预警延迟使用 1.60、1.50、1.40、1.30、1.20、1.10、1.00 秒，危险持续 0.45 秒，均为明确标注的演示参数，不能写入实际射线识别器作为默认机制。
- 宽度沿用草图示意 0.40/0.51；人物半径 0.08、移动速度 2.5 个落石半径/秒同样未经游戏校准。
- 额外射线与死亡的因果关系不能由当前画面可靠确认；本次不宣称复刻了死亡后必出的随机射线。
- 模拟参数下被击中会标红并显示风险；脚本仍继续展示后续提示，不把它当作游戏复活或无敌。倒计时归零也不立即宣称实战安全。

实际覆盖层仍只消费识别器提供的绝对时刻，不使用本文件的演示时序。共享 Canvas 页面能打开，但内容接口未能读取，因此没有声称核实其源码公式。

## 重建新版 GIF

在仓库根目录执行（需先完成前端构建，见 handoff）：

```powershell
$env:DILMETER_BRONTAS_CADENCE_OUT = "$PWD\docs\demos\brontas-guide\frames-cadence.json"
Push-Location cn-rt
go test ./cmd/dilmeterapi -run '^TestExportBrontasCadenceDemo$' -count=1
Pop-Location
Remove-Item Env:DILMETER_BRONTAS_CADENCE_OUT
Push-Location docs/demos/brontas-guide
npm install
node render.mjs frames-cadence.json brontas-guide-demo.gif
Pop-Location
```

### 九宫格修正

视频里的通道标号不再当成 `offset` 直接使用。`cadence-reference.json` 改为 `lanes`（0/1/2）和统一 `grid`，所有射线用相同边界生成，详见 `brontas-guide.md` 的九宫格约束。此前 GIF 中两条相邻纵线之间的窄缝不存在，不能用作落点。
